# Freshroots Reorder Desk

The web app for the Freshroots demand-planning engine (MESA Case 01). It is built with Next.js 16 and deployed on Vercel.

Twice a week, the analyst uploads the SAP export. The engine applies Raghav's documented rules to every SKU, and Gemini drafts a short brief. Procurement then approves, edits or rejects each reorder. Approved lines are exported as CSV, one purchase order per distributor, for import into Zoho Inventory. The app never sends anything to a supplier.

## Pages

| Page | What it's for |
|---|---|
| `/` Decisions | The planner brief, KPIs, and one row per SKU showing weeks of stock against its allowed range, demand, what the engine recommends, and the person's decision |
| `/sku/[id]` | Why the engine decided what it did, weekly sales against the 12-week and 4-week averages, the numbers behind the decision, data checks, and decision history |
| `/orders` | Approved lines grouped by distributor, override rate, pending decisions, and CSV export |
| `/data` | Upload a new export, run history, input file fingerprints, the data-quality report, and the activity log |
| `/rules` | The rules drawn as instruments, plus the **rulebook**: why each rule exists, edge cases, owner, the conflict map, variables vs constants, a Markdown download and "Ask the rulebook" |
| `/oversight` | The monthly review: outcomes per run (not usage), early-warning log, drift log, rule-conflict log, failure playbook with named owners, accountability and adoption |
| `/compare` | Any run against the one before it, or a scenario against its original: operations applied, KPI deltas, early warnings, drift, per-SKU changes |

## Design system ("The Freshroots Control Room")

- **Tokens.** All tokens live in `src/app/globals.css`: palette, spacing, radii, elevation and motion.
- **Surfaces and colour ("Kokum & Turmeric", graded from the Konkan coast).**
  - Deep kokum plum (`night`) carries context: the sidebar, hero and detail headers.
  - Warm rice paper (`paper`) carries work: tables, forms and panels.
  - Turmeric (`spice`) is the single accent and the demand core of the orbit.
  - Status has its own colours: vermilion below range (stockout risk), monsoon indigo above range (overstock), leaf green in range, and amber for data warnings only.
- **Typography.** Bricolage Grotesque for display, Inter for data, with tabular numerals throughout.
- **Signature object.** `OrbitCore` is pure CSS 3D with no library. Each point is a real SKU, placed on the orbit for its decision. It pauses when off-screen and stays still under `prefers-reduced-motion`.
- **Data-driven visuals.**
  - `CoverGauge` (weeks of stock against the SKU's own range) and `DemandPulse` (last 12 weeks, plus the 4-week and 12-week averages) read the engine's values and never recalculate them.
  - `tests/insights.test.ts` checks that both visuals agree with the engine's flags on every dataset.
- **Interaction.** Toasts appear only after the server confirms an action. Undo and partial exports ask for confirmation. The SKU drawer syncs to `?sku=` and closes on Escape.

## Operating safely over time (from the "agent failures and drift" class)

- **Database simulation (Scenario lab on `/data`).** Copies a real run's tables and applies named operations, for example the SKU009 exercise: `DELETE` its sales, `INSERT` a new distributor, `UPDATE` its distributor. It then reruns the engine and opens a comparison. Scenario runs never become the default view, never notify anyone, and the API refuses approval and PO export for them (409). `scripts/simulate_new_sku.py` does the same on the CSVs.
- **Fail loudly.** A "Needs attention" banner at the top of the desk lists every run warning, data hold, early warning and rule conflict.
- **Rule conflicts.** `src/lib/conflicts.ts` detects where two rules disagree (surge vs overstock, the festival uplift flipping a decision, an order too small or too big for the range, a data hold vs stockout risk, the calendar vs the rule). Each instance is logged as an event. Precedence and owners are mapped in `src/lib/governance.ts`.
- **Drift and early warnings.** `src/lib/compare.ts` compares each run with the previous real run (or a scenario with its base) and flags:
  - new or removed SKUs and distributors, and changed export columns;
  - orders that jump by 50% or more (the chia seeds 100 → 180 case), overstock-to-stockout swings, demand shifts of 30% or more, and lost history.
  Alerts go to Telegram and/or a Slack incoming webhook (`SLACK_WEBHOOK_URL`), and are simulated and logged until those are set.
- **Trust friction.** Every approval needs a confirm step that restates the quantity and stock. There is deliberately no "approve all".
- **Institutional memory.** `docs/RULEBOOK.md` is generated by `/api/rulebook`. "Ask the rulebook" answers from the rulebook only (Gemini, or keyword search without a key) and cites sections.
- **Consolidated table.** The "One consolidated table" export on `/data` restructures the five input files into one row per SKU.

## How it fits together

- **Engine.** `src/lib/engine/` is a TypeScript port of `../freshroots_engine.py`. `tests/parity.test.ts` checks that both engines produce identical decisions, data-quality records and explanations on three datasets: the real export, the sample data and a deliberately messy fixture. After changing either engine, regenerate the golden files with `../.venv/bin/python ../scripts/export_golden.py`.
- **Brief.** `src/lib/brief.ts` builds the brief. Gemini writes it from the engine's facts. If the draft contains any number the engine didn't produce, it is replaced by a template. With no API key, the template is always used.
- **Decisions.** `src/lib/decisions.ts` handles decisions. Each one stores a name. Changing or rejecting a reorder requires a reason, and those changes count towards the override rate.
- **Storage.** `src/lib/store/` uses Postgres when `DATABASE_URL` is set and memory otherwise. The tables (`runs`, `decisions`, `events`) are created on first use.
- **Notifications.** `src/lib/notify.ts` sends a Telegram message to procurement when a run lands. Without the Telegram keys it is simulated, and the activity log records what would have been sent.
- **First run.** On first use, the app creates a run from the bundled SAP sample export in `data/`.

## Develop

```bash
npm install
cp .env.example .env.local   # optional; everything works without keys
npm run dev
```

npm test && npm run typecheck && npm run lint
